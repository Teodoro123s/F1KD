# Horizontal Refactoring Strategy - Complete Guide\n\n## 🎯 Mission\n\nTransform **monolithic, hard-to-maintain React components** into **modular, testable, scalable code** by applying a proven 6-layer architecture pattern.\n\n**Result**: Cleaner code, faster debugging, easier feature development.\n\n---\n\n## 📐 The 6-Layer Architecture\n\nEach refactored page follows this vertical architecture:\n\n```\nLayer 1: Presentation (JSX Only)\n┌─────────────────────────────────────────┐\n│ Component (< 100 lines)                 │\n│ ✓ Only renders JSX                      │\n│ ✓ Composes hooks and components         │\n│ ✗ No business logic                     │\n│ ✗ No state management (except UI)       │\n└─────────────────────────────────────────┘\n                    ↓\nLayer 2: State Orchestration (Hooks)\n┌─────────────────────────────────────────┐\n│ 3-4 Custom Hooks                        │\n│ ✓ Manage React state & effects          │\n│ ✓ Compose pure utilities                │\n│ ✓ Return organized state objects        │\n│ ✗ No rendering (no JSX)                 │\n│ ✗ No direct API calls                   │\n└─────────────────────────────────────────┘\n                    ↓\nLayer 3: Business Logic (Pure Utilities)\n┌─────────────────────────────────────────┐\n│ 10-20 Pure Functions                    │\n│ ✓ Filter, validate, transform data      │\n│ ✓ Build API payloads                    │\n│ ✓ Generate exports                      │\n│ ✗ No React dependencies                 │\n│ ✗ No side effects                       │\n│ ✗ No API calls                          │\n└─────────────────────────────────────────┘\n                    ↓\nLayer 4: API & Context (External)\n┌─────────────────────────────────────────┐\n│ External Services                       │\n│ - REST API calls (apiGetChildren, etc)  │\n│ - Context (useAuth, useMothers)         │\n│ - localStorage (persistence)            │\n└─────────────────────────────────────────┘\n```\n\n---\n\n## 📚 Documentation Files\n\n### 1. **ARCHITECTURE.md** (ProgressReport)\n   - 🎓 Key Principles\n\n### 1. **Separation of Concerns**\nEach layer has one job:\n- **Layer 1**: Render UI\n- **Layer 2**: Orchestrate state\n- **Layer 3**: Transform data\n- **Layer 4**: External I/O\n\n### 2. **Never Rewrite, Refactor Horizontally**\n- Extract logic without changing behavior\n- Move code, don't rewrite it\n- UI rendering stays identical\n- No breaking changes\n\n### 3. **Pure Functions First**\n- Start with utilities (Layer 3)\n- No React dependencies\n- No side effects\n- Fully testable\n\n### 4. **Composition Over Inheritance**\n- Hooks compose utilities\n- Components compose hooks\n- Each layer is pluggable\n- Easy to add/remove features\n\n---\n\n## 🧪 Testing at Each Layer\n\n### Layer 3: Business Logic (Pure Utilities)\n```javascript\n// ✅ Trivial to test - no mocks needed\ntest('filterRows should only return rows matching filter', () => {\n  const rows = [{school: 'A'}, {school: 'B'}];\n  const result = filterRows(rows, {school: 'A', ...});\n  expect(result).toHaveLength(1);\n});\n```\n\n### Layer 2: State Hooks\n```javascript\n// ✅ Testable with React Testing Library\ntest('useProgressFilters should update filteredRows on setSchool', () => {\n  const { result } = renderHook(() => useProgressFilters({...}));\n  act(() => result.current.setSchool('New School'));\n  expect(result.current.filteredRows.length).toBeLessThan(previous);\n});\n```\n\n### Layer 1: Component\n```javascript\n// ✅ Integration test - end-to-end\ntest('ProgressReport should display filtered data when filter applied', () => {\n  render(<ProgressReport />);\n  const input = screen.getByPlaceholderText('Search');\n  fireEvent.change(input, { target: { value: 'risk:true' } });\n  expect(screen.getAllByTestId('risk-row')).toHaveLength(expected);\n});\n```\n\n---\n\n## 🚀 Scaling Pattern\n\nThis pattern scales because:\n\n1. **Utilities are reusable**\n   - Use in multiple pages\n   - Use in backend tests\n   - Use in other hooks\n\n2. **Hooks are composable**\n   - Combine multiple hooks\n   - Create meta-hooks\n   - Share across pages\n\n3. **Components are modular**\n   - Small, focused components\n   - Easy to test in isolation\n   - Easy to refactor\n\n### Example: Adding \"Export by Email\" Feature\n\n**Old Way** (Monolithic):\n- Add 50+ lines to component\n- Add state variable\n- Add useEffect\n- Add function\n- Risk breaking existing code\n\n**New Way** (Layered):\n- Add 1 pure utility function: `generateEmailPayload(rows, format)`\n- Add 1 hook method: `useReportExport` → add `emailExport` option\n- Add 1 button in component\n- No risk to existing code\n\n---\n\n## 📋 Quick Reference\n\n### File Organization Pattern\n```\nPageName/\n├── PageName.jsx              # Layer 1: Component\n├── pageNameUtils.js          # Constants, helpers\n├── utils/                    # Layer 3: Business Logic\n│   ├── filterUtils.js\n│   ├── exportUtils.js\n│   ├── apiUtils.js\n│   └── columnUtils.js\n├── hooks/                    # Layer 2: State Orchestration\n│   ├── usePageFilters.js\n│   ├── usePageData.js\n│   └── usePageForms.js\n├── components/               # Layer 1: Sub-components\n│   ├── PageToolbar.jsx\n│   ├── PageTable.jsx\n│   └── PageModal.jsx\n├── ARCHITECTURE.md           # Documentation (this layer)\n└── README.md                 # How to use this page\n```\n\n### JSDoc Template\n```javascript\n/**\n * filename.js - Brief description\n * \n * RESPONSIBILITY: What this file does\n * LAYER: [Business Logic | State Orchestration | Presentation]\n * DEPENDENCIES: What it imports\n * EXPORTS: What it provides\n * \n * USAGE:\n *   [Example code]\n */\n\n/**\n * functionName - What it does\n * \n * @param {Type} paramName - Description\n * @returns {Type} Description\n * @example\n *   [Usage]\n */\nexport const functionName = (...) => { ... }\n```\n\n---\n\n## ✅ Checklist: Before

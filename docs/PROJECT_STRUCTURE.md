# Project Structure

This guide is a map for finding code and deciding where new code belongs. F1KD is organized by **application layer** at the top level and by **feature** inside the frontend. Keep a change inside the feature that owns it unless another feature genuinely needs to share it.

## Start here

```text
F1KD/
  src/                    React frontend
  server/                 Express API and database access
  docs/                   Setup, user, and developer guides
  .github/workflows/      Automation such as the public demo deployment
  docker-compose*.yml     Local services and optional TLS configuration
  Dockerfile              Frontend production image
  package.json            Frontend commands and dependencies
  README.md               Setup and links to the guides
```

`dist/` is generated by the frontend build. `node_modules/`, `.env`, database files, and uploaded files are dependencies, local configuration, or runtime data—not source-code locations.

## How a request moves through the app

```text
Browser
  -> src/main.jsx
  -> src/App.jsx                  routes and access gates
  -> src/pages/<Feature>/         page and feature-specific UI/state
  -> src/api/<resource>.js        authenticated HTTP client
  -> server/index.js              Express app and route mounting
  -> server/routes/<resource>.js  endpoint and request orchestration
  -> server/middleware/           authentication, authorization, uploads, errors
  -> server/services/             reusable backend operations
  -> server/utils/                backend-only rules and validation
  -> server/db.js                 MariaDB schema and connection
```

Database-backed documents use MinIO through the backend. The browser should call `src/api/`; it should not connect directly to the database or object storage.

## Frontend map

```text
src/
  main.jsx
  App.jsx
  api/                 One HTTP client per backend resource
  auth/                Login state and session lifecycle
  components/          App-wide layout and reusable UI
    ui/                Shared buttons, dialogs, pagination, tables, and status components
  context/             React state shared by multiple routes
  pages/               Route-level features
  styles/              Global styles, tokens, and shared component styles
  utils/               Small rules shared by multiple features
  demo/                Synthetic, read-only public demo
  assets/              Images and static assets
```

### Route-level features

Each folder under `src/pages/` owns one route or related workflow:

| Folder | Responsibility |
|---|---|
| `AISetting/` | AI settings and report assistant |
| `Auth/` | Sign-in and authentication screens |
| `Beneficiary/` | Beneficiary list and child/mother records |
| `Community/` | Schools, groups, batches, and their UI |
| `Dashboard/` | Role-aware dashboard |
| `Monitoring/` | Monitoring and check-up workflows |
| `Notifications/` | Notification inbox and preferences |
| `Profile/`, `Settings/` | User profile and app settings |
| `Program/` | Programs, receipts, and program reports |
| `ProgressReport/` | Report setup, results, graphs, and exports |
| `Reports/` | Operational reporting |
| `UserManagement/` | User administration |

Put feature-only components, hooks, utilities, and tests beside the feature that uses them. For example:

```text
src/pages/ProgressReport/
  ProgressReport.jsx
  progressReportConfig.js
  components/
  hooks/
  utils/
```

The empty `hooks/` folders are available for feature-specific hooks; they do not mean hooks should be placed there if the feature has none yet.

Beneficiary child and mother workflows live in `src/pages/Beneficiary/child/` and `src/pages/Beneficiary/mother/`. Some files at the `Beneficiary/` root are compatibility re-exports for older import paths. Put new implementations in the relevant child or mother folder and use that canonical path for new imports.

Use `src/components/` only for UI shared by independent features. Use `src/utils/` for framework-independent helpers shared across features, grouped by concern (for example `beneficiary/`, `formatting/`, `navigation/`, and `validation/`). Keep feature-only helpers in that feature's `utils/` folder.

### Shared motion and transitions

Shared animation durations and easing curves are defined as CSS variables in `src/styles/variables.css`. Shared transition and entry/exit styles live in `src/styles/`; use those tokens rather than adding one-off timings. `src/components/ui/usePresence.js` keeps shared overlays mounted during their exit transition. Reuse it for new conditionally rendered overlays, and make closing content inert so it cannot receive input while fading out. Native select option menus are controlled by the browser and should not be given custom popup animations.

`src/index.css` is the global stylesheet entry point. It imports Tailwind theme/utilities without Preflight, then the established `src/styles/main.css` component styles and the view-token, modal, table, form, and AI-settings layers. Tailwind is being introduced incrementally; preserve existing design tokens and migrate component styles only when verified. `main.css` imports `variables.css` before its component styles; do not import the same token file again from `index.css`.

The Vite development proxy in `vite.config.js` targets the backend's default port, `4000`. Set `VITE_API_PROXY_TARGET` when the backend runs elsewhere.

Creation forms that need school/group/batch assignments should use the scoped `/api/community/reference-options` endpoint instead of loading the full operational `/api/community/summary`. The reference response intentionally excludes beneficiary profile data and follows the authenticated user's school/group scope.

## Backend map

```text
server/
  index.js        Express app, middleware, and route mounting
  db.js           Database connection and schema setup
  routes/         HTTP endpoints and request-level orchestration
  middleware/     Authentication, authorization, uploads, and errors
  services/       Reusable backend operations
  utils/          Server-only rules, validation, and helpers
  migrations/     Ordered SQL changes for existing databases
  data/           Runtime data, including local-upload fallback
  test/           Backend unit and integration tests
  README.md       Backend-specific operations and behavior
```

Keep SQL and authorization decisions on the server. Routes should use the existing middleware and service patterns; do not make a frontend API client import backend modules.

### Database setup files

- `server/db.js` owns the connection pool and runs the application's idempotent schema checks during backend startup.
- Dated SQL files under `server/migrations/` are explicit schema changes for existing databases; use the relevant migration instructions in `server/README.md`.
- `server/migrations/compiled_schema.sql` identifies itself as a fresh-database schema and directs existing databases to use individual migrations.
- `server/create_users.sql` and `server/f1kd_recreate.sql` are also fresh-database SQL scripts. Their schema parity with the runtime bootstrap and compiled schema has not been established, so treat them as separate legacy/manual entry points until a dedicated schema comparison confirms which should be maintained.

Do not edit only one schema representation when changing the database. First compare the intended fresh-install and upgrade paths, then update and test the appropriate bootstrap and migration files together.

Community mother transfers use `PUT /api/community/mothers/:id/batch`. The API validates the destination against the mother's school and group, then updates the mother and all linked children in one transaction so child batch assignments continue to follow their mother.

Archived-record retention is implemented in `server/services/archiveRetention.js` and started by `server/index.js`. The job uses the nine-month archive age, purges eligible records and linked descendants transactionally, and queues failed uploaded-file deletions for retry. Keep `server/db.js`, `server/migrations/20261102_archive_retention.sql`, and `server/migrations/compiled_schema.sql` consistent when changing the retry-queue schema. The service is covered by `server/test/archive_retention.test.js`.

The shared responsive pagination UI lives in `src/components/ui/Pagination.jsx` with its styles in `src/styles/components/tables-common.css`. Feature pages may wrap it to preserve an existing public component API, while each feature continues to own page state and data-fetch behavior.

## Tests and common commands

- Frontend tests are generally next to the helper they cover, such as `src/pages/ProgressReport/utils/cohortSummary.test.mjs`.
- Backend tests live in `server/test/`.
- `npm run build` checks the production frontend build.
- `npm test` runs the configured project test suite.
- `npm run test:progress-report-csv` runs focused Progress Report CSV/table utility tests.
- `cd server && npm run dev` starts the API for direct backend development; Docker Compose is the normal full-stack setup.

When adding a helper, put its test beside it. When changing a route or service, add or update the relevant test under `server/test/`.

## Where to put a change

1. Find the route in `src/App.jsx`.
2. Put page UI and feature state in `src/pages/<Feature>/`.
3. Put HTTP calls in the matching `src/api/` client; add or update the matching server route in `server/routes/`.
4. Put reusable server operations in `server/services/`; put server-only validation/rules in `server/utils/`.
5. Add a test next to a frontend utility or in `server/test/` for backend behavior.
6. Update the relevant guide under `docs/` when setup or user-visible behavior changes.

Prefer focused changes over moving many files at once. If a file is moved, update its imports in the same change, preserve any compatibility re-export that callers still use, then run the frontend build and relevant tests.
